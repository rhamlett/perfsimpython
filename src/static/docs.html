🎯 Performance Problem Simulator

An educational Azure App Service application that intentionally creates performance problems for learning and demonstration purposes.

Purpose

This application is designed to help Azure App Service Support engineers and Technical Advisors:

📖
Learn How to diagnose common performance issues in Azure App Service
🔧
Practice Using Azure diagnostics and monitoring tools
🎭
Demonstrate Performance anti-patterns in a controlled environment
👥
Train Support teams on identifying and resolving performance problems

⚠️ Warning - This application intentionally creates performance problems!

  • 🔥 CPU stress - Creates worker processes running intensive operations to consume CPU cores
  • 📊 Memory pressure - Allocates and holds memory blocks to increase working set
  • 🧵 Event loop blocking - Uses sync-over-async anti-patterns to block Python's asyncio event loop
  • 🐌 Slow requests - Generates long-running requests for profiler analysis
  • 💥 Application crashes - Triggers fatal crashes for testing Azure Crash Monitoring
  • ❌ Failed requests - Generates HTTP 5xx errors for testing AppLens and Application Insights

Only deploy this application in isolated, non-production environments.

🚀 Quick Start

Run Locally

# Clone the repository git clone https://github.com/rhamlett/perfsimpython.git cd perfsimpython # Create virtual environment and install dependencies python -m venv venv source venv/bin/activate # On Windows: venv\Scripts\activate pip install -r requirements.txt # Run the application uvicorn src.main:app --reload --host 0.0.0.0 --port 8000 # Open in browser # Dashboard: http://localhost:8000

Run Tests

# Run all tests pytest # Run with coverage pytest --cov=src --cov-report=html

⚙️ Environment Variables

The following environment variables can be configured to customize application behavior. These are optional and primarily useful when deploying to Azure App Service.

Variable Description Default
HEALTH_PROBE_RATE Health probe interval in milliseconds (default: 200, minimum: 100). Lower values provide more granular latency data but increase overhead during profiling. 200
IDLE_TIMEOUT_MINUTES Minutes of inactivity before suspending health probes (default: 20). Reduces network traffic and Application Insights telemetry when idle. 20
PAGE_FOOTER Custom HTML footer text displayed at the bottom of the dashboard. Supports HTML links for attribution. None

HEALTH_PROBE_RATE

Controls how frequently the dashboard probes the application for latency measurement. Lower values provide more granular data but can cause probe overlaps during profiling.

  • Default: 200ms (5 probes/second)
  • Minimum: 100ms (values below this are clamped)
  • Chart updates: The latency chart always updates at 100ms using interpolation

Setting via Azure CLI:

az webapp config appsettings set \ --resource-group rg-perfsimpython \ --name perfsimpython \ --settings HEALTH_PROBE_RATE=400

IDLE_TIMEOUT_MINUTES

When the application is idle (no dashboard connections or load test requests), health probes are automatically suspended to reduce unnecessary network traffic to Azure's frontend, AppLens, and Application Insights.

  • Default: 20 minutes
  • Wake-up: Simply reload the dashboard or send any API request
  • Activity sources: Dashboard page loads, API calls (load test traffic counts as activity)
  • Disable: Set to 0 to disable idle mode completely

Setting via Azure CLI:

az webapp config appsettings set \ --resource-group rg-perfsimpython \ --name perfsimpython \ --settings IDLE_TIMEOUT_MINUTES=30

PAGE_FOOTER

The PAGE_FOOTER environment variable allows you to customize the footer credits displayed on the dashboard. This is useful for attributing tools, teams, or linking to relevant resources.

Example Value:

Setting via Azure CLI:

az webapp config appsettings set \ --resource-group rg-perfsimpython \ --name perfsimpython \ --settings PAGE_FOOTER='Created by <a href="https://speckit.org/" target="_blank">SpecKit</a>'

Setting Locally:

📊 Dashboard

The application includes a real-time dashboard at the root URL that shows:

  • CPU usage - Current processor utilization
  • Memory - Working set (physical memory used by the process)
  • Active threads - Thread count in the process
  • Pending tasks - Asyncio tasks queued in the event loop
  • Request latency - Real-time probe response time (shows impact of event loop blocking)
  • Active simulations - Currently running problem simulations

The dashboard uses WebSockets for real-time updates and includes a side panel with controls to trigger each type of simulation.

Metric Color Indicators

The CPU and Memory metric tiles use dynamic color coding to indicate resource utilization levels:

Color Utilization Status
Black (default) 0-60% Normal - resources are within acceptable range
Yellow 60-80% Warning - elevated usage, approaching concerning levels
Red >80% Danger - high usage, potential resource exhaustion

Event Log & Simulation IDs

The Event Log at the bottom of the dashboard records all simulation activity with color-coded entries matching each simulation type. Messages related to a specific simulation instance are marked with a dotted underline.

Viewing Simulation IDs: Hover over any underlined message to reveal the full Simulation ID (GUID) in a tooltip. This ID uniquely identifies each simulation instance.

Using Simulation IDs for Troubleshooting:

  • The same Simulation ID is logged server-side and appears in Azure Application Insights and Log Analytics
  • Use this ID to correlate dashboard events with server logs when analyzing performance issues
  • Filter Azure logs by Simulation ID to isolate telemetry from a specific simulation run
  • See the Azure Diagnostics Guide for detailed correlation techniques

⏱️ Request Latency Monitor

The dashboard includes a Request Latency Monitor that demonstrates how event loop blocking affects real-world request processing. The latency values shown include both queue time and processing time.

How It Works

  • A background task continuously probes the /api/health/probe endpoint
  • Latency is measured end-to-end: request sent → response received
  • Results are broadcast via WebSocket to the dashboard in real-time

What You'll Observe

Condition Latency Status Explanation
Normal operation < 150ms 🟢 Good Event loop threads available
Mild blocking 150ms - 1s 🟡 Degraded Requests queued waiting for event loop
Severe blocking > 1s 🔴 Severe Significant queuing delay
Timeout 30s 🔴 Critical Event loop completely blocked

Why This Matters

During event loop blocking, CPU and memory metrics often look normal, but users experience severe latency. The latency monitor makes this invisible problem visible — you can watch response times spike from milliseconds to seconds when triggering the async blocking simulation.

🔥 CPU Stress Simulation

The CPU Stress simulation creates high CPU usage through parallel worker processes running intensive cryptographic operations, saturating available CPU cores for a specified duration.

How It Works

The simulation spawns worker processes (using Python's multiprocessing) that execute intensive SHA-256 hash calculations in tight loops. Unlike the main asyncio event loop, these worker processes can fully utilize multiple CPU cores without blocking the application's request handling.

Dashboard Controls

  • Duration: How long to run the stress test (minimum 1 second)
  • Intensity: Moderate or High - controls number of parallel workers
  • Start/Stop: Begin or cancel the simulation

What You'll Observe

Metric Expected Explanation
CPU % High (depends on intensity) Worker processes consuming CPU cycles
Memory Slight increase Worker processes have small memory footprint
Latency May increase slightly Less CPU available for request processing

Real-World CPU Issues

High CPU in production is typically caused by:

  • Inefficient algorithms (O(n²) when O(n) is possible)
  • Infinite loops due to bugs
  • Excessive regular expression backtracking
  • Unoptimized data processing with large datasets
  • CPU-bound operations blocking the event loop instead of being offloaded

Diagnosis Tools

  • Azure App Service → Diagnose and Solve Problems → CPU usage
  • Application Insights Performance blade
  • py-spy for profiling Python processes
  • top / htop for real-time CPU monitoring

📊 Memory Pressure Simulation

The Memory Pressure simulation allocates and holds large byte arrays to demonstrate memory consumption patterns and garbage collection behavior.

How It Works

Large bytearray objects are allocated and filled with random data to prevent memory optimization. These allocations are held in a list, simulating problematic allocation patterns like memory leaks. Multiple allocations are cumulative until explicitly released.

Dashboard Controls

  • Size (MB): Amount of memory to allocate per click
  • Allocate: Adds a new memory block (cumulative)
  • Release: Frees all allocated blocks

What You'll Observe

Metric Expected Explanation
Memory (MB) Increases by allocation size Charts reflect working set increase
CPU Brief spike Memory allocation and data filling
After Release Memory drops Python garbage collector reclaims memory

Python Memory Management

Python uses automatic memory management with garbage collection. Key considerations:

  • Large allocations may not be immediately returned to the OS even after release
  • Python's memory allocator maintains pools for small objects
  • Reference cycles require the cyclic garbage collector to clean up
  • gc.collect() can force garbage collection but doesn't guarantee memory is returned to OS

Real-World Memory Issues

  • Collections that accumulate data without limits (e.g., caches, logs)
  • Circular references preventing garbage collection
  • Global variables holding large objects
  • Event handlers or callbacks keeping references alive
  • Large file reads loaded entirely into memory

Diagnosis Tools

  • Azure App Service → Memory Working Set blade
  • tracemalloc for tracking memory allocations in Python
  • memory_profiler for line-by-line memory analysis
  • objgraph for visualizing object references

🧵 Async Blocking (Event Loop Starvation)

The Async Blocking simulation demonstrates the dangerous "sync-over-async" anti-pattern in Python, where synchronous blocking calls are made inside async functions, freezing the entire event loop.

How It Works

The simulation calls time.sleep() (a blocking operation) inside an async context instead of using await asyncio.sleep(). This blocks Python's single-threaded event loop, causing:

  1. The event loop thread becomes blocked
  2. ALL other async operations freeze (including other requests)
  3. Incoming requests queue up waiting for the event loop
  4. Request latency spikes dramatically

Dashboard Controls

  • Delay (s): How long each blocking operation lasts
  • Count: Number of concurrent blocking operations to spawn
  • Start/Stop: Begin or cancel the simulation
⏱️ Duration Note: Python's asyncio runs on a single thread by default. Even a few blocking operations can cause significant impact — much more dramatic than thread pool starvation in multi-threaded frameworks.

The Sync-Over-Async Anti-Pattern

These patterns block the event loop and should be avoided:

# ❌ BAD - Blocks event loop import time async def handle_request(): time.sleep(5) # BLOCKS the entire event loop! return "Done" async def fetch_data(): response = requests.get(url) # BLOCKS - requests is synchronous! return response.json()
# ✅ GOOD - Properly async import asyncio import httpx async def handle_request(): await asyncio.sleep(5) # Yields control back to event loop return "Done" async def fetch_data(): async with httpx.AsyncClient() as client: response = await client.get(url) # Non-blocking HTTP return response.json()

What You'll Observe

Metric Expected Explanation
CPU LOW Event loop is waiting, not working
Memory Normal No memory leak occurring
Pending Tasks May increase Tasks queued waiting for event loop
Latency 🔴 Spikes to seconds Requests queued waiting for event loop

Why CPU is Low but Latency is High

This is the signature of event loop blocking. The CPU isn't working because the event loop is blocked waiting. New requests can't start because the single event loop is occupied. It looks like the app is idle, but users experience timeouts.

Real-World Causes

  • Using synchronous libraries in async code: requests.get() instead of httpx or aiohttp
  • Calling time.sleep() instead of await asyncio.sleep()
  • Synchronous file I/O without aiofiles
  • Synchronous database drivers without async equivalents
  • Third-party libraries that block internally
  • CPU-intensive operations that should be offloaded to a thread pool

How to Fix

  • Use await with proper async libraries throughout
  • Replace requests with httpx or aiohttp
  • Use asyncio.to_thread() to offload blocking operations
  • Use aiofiles for async file operations
  • Use async database drivers (e.g., asyncpg, aiomysql)

Diagnosis Tools

  • Response times spike for ALL endpoints simultaneously
  • Azure App Service → Diagnose and Solve Problems
  • py-spy to see what the event loop thread is doing
  • Custom asyncio event loop monitoring with loop.slow_callback_duration

🐌 Slow Request Simulator

The Slow Request Simulator generates long-running requests (~25 seconds each) specifically designed for profiler training and Azure diagnostics practice.

Purpose

Unlike the Async Blocking simulation (which causes many short blocks), this creates individual long requests that are clearly visible in profiler traces and monitoring dashboards. The extended duration makes it easy to capture them in diagnostic tools.

Dashboard Controls

  • Duration (s): How long each request takes (5-60 seconds, default 25)
  • Interval (s): Time between requests
  • Max Requests: Total requests to generate
  • Start/Stop: Begin or cancel the simulation

Recommended Settings

For a 60-second profiler trace:

  • Duration: 25 seconds (allows capture within trace window)
  • Interval: 10 seconds (multiple samples)
  • Max Requests: 6 (doesn't overwhelm the system)
⚠️ Note on Queue Time: If the event loop is blocked, you may see additional delay before the request starts. This is "Queue Time" (waiting for event loop) vs "Execution Time" (running the code).

Using with Azure Diagnostics

  1. Start a CPU Profiler trace (60-120 seconds) in Azure Portal
  2. Click 🐌 Start Slow Requests in the dashboard
  3. Wait for trace to complete
  4. Download and analyze - look for the long-running requests

See the Azure Diagnostics Guide for detailed profiler analysis instructions.

❌ Failed Requests Simulation

The Failed Requests simulation generates HTTP 5xx errors for testing Azure diagnostics tools like AppLens and Application Insights.

Purpose

This simulation generates HTTP 500 Internal Server Error responses that are visible in:

  • AppLens - Azure Portal → Diagnose and solve problems
  • Application Insights - Failures blade
  • Azure Monitor - Error rate alerts

Dashboard Controls

  • Error Count: Number of HTTP 500 errors to generate (1-100)
  • Generate: Triggers the error generation

💥 Crash Simulation

The dashboard includes a Crash Simulation feature for testing Azure crash monitoring and container restart behavior.

⚠️ Warning - This will TERMINATE the application!

Crash simulations immediately terminate the process. Azure App Service will automatically restart the application after a crash. Make sure you have monitoring enabled before triggering a crash.

Available Crash Types

Type Description Use Case
exception Raises an unhandled exception that crashes the process General crash testing (recommended)
stackoverflow Infinite recursion causing stack overflow Stack trace analysis practice
oom Allocates memory until the process crashes Memory dump analysis
sigabrt Sends SIGABRT signal to terminate process Testing signal handling / Docker restart

Azure Crash Monitoring Setup

  1. In Azure Portal, go to your App Service
  2. Navigate to Diagnose and solve problems
  3. Search for "Application Crashes"
  4. Enable crash monitoring if available
  5. Trigger a crash using the dashboard
  6. Observe the container restart and analyze logs
