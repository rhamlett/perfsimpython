🎯 性能问题模拟器

一个教育 Azure App Service 应用 故意制造性能问题 用于学习和演示目的。

目的

该应用程序旨在帮助 Azure App Service 支持工程师和技术顾问：

📖
学习 如何诊断Azure App Service常见的性能问题
🔧
实践 使用 Azure 诊断和监测工具
🎭
演示 受控环境中的性能反模式
👥
列车 支持团队识别和解决绩效问题

⚠️ 警告——本应用故意制造性能问题！

  • 🔥 CPU 压力 - 创建运行密集操作以消耗 CPU 核心的工作进程
  • 📊 记忆压力 - 分配并保留内存块以增加工作集
  • 🧵 事件环阻断 - 使用 sync-over-async 反模式阻挡Python的非同步事件循环
  • 🐌 慢速请求 - 生成长期的分析请求
  • 💥 应用程序崩溃 - 触发致命坠机测试 Azure 碰撞监测
  • ❌ 失败的请求 - 产生 HTTP 个5xx错误用于测试 AppLens 和测试 Application Insights

仅在隔离的非生产环境中部署此应用。

📊 仪表盘

该应用在根URL处包含一个实时仪表盘，显示：

  • CPU 用法 - 当前处理器利用率
  • 记忆 - 工作集（进程使用的物理内存）
  • 活跃线程 - 工艺中的线程数
  • 待处理任务 - 事件循环中排队的非同步任务
  • 请求延迟 - 实时探针响应时间（显示事件环路阻断的影响）
  • 主动仿真 - 目前正在运行问题模拟

仪表盘使用WebSockets进行实时更新，并包含带有触发每种模拟类型的控制面板。

公制颜色指示器

CPU和内存度量图块使用动态颜色编码来表示资源利用率水平：

颜色 利用情况 现状
黑色（默认） 0-60% 正常——资源在可接受范围内
黄色 60-80% 警告——使用率升高，接近令人担忧的水平
红色 >80% 危险——高使用率，潜在资源枯竭

事件日志与仿真ID

仪表盘底部的事件日志记录所有仿真活动，并以颜色编码的条目对应各仿真类型。与特定仿真实例相关的消息用虚线下划标记。

观看模拟ID： 将鼠标悬停在任何下划线的消息上，即可在提示中显示完整的仿真ID（GUID）。该ID唯一标识每个仿真实例。

使用仿真ID进行故障排除：

  • 同一仿真ID在服务器端记录，并出现在 Azure Application Insights 和Log Analytics中
  • 在分析性能问题时，利用该ID将仪表盘事件与服务器日志关联起来
  • 通过模拟ID过滤 Azure 日志，以将遥测数据与特定仿真运行隔离开来
  • 参见 Azure 诊断指南 详细的相关技术

⏱️ 请求延迟监控器

仪表盘包含请求延迟监控器，展示了事件循环阻断如何影响现实世界的请求处理。显示的延迟值包括队列时间和处理时间。

工作原理

  • 一个后台任务持续探测 /api/health/probe 终点
  • 延迟是端到端测量的：请求发送→响应
  • 结果通过 WebSocket 实时广播到仪表盘

你将观察到的内容

状况 延迟 现状 解释
正常运行 < 150毫秒 🟢 很好 可用的事件循环线程
轻度阻挡 150毫秒 - 1秒 🟡 退化 等待事件循环的请求队列
严重阻塞 > 1 🔴 严重 显著的排队延迟
暂停 30多岁 🔴 批判 事件循环完全阻塞

为什么这很重要

在事件循环阻断期间， CPU 和内存指标通常看起来正常，但用户却会遇到严重的延迟。延迟监控器让这个隐形问题变得可见——当触发异步阻挡模拟时，你可以看到响应时间从毫秒激增到几秒。

🔥 CPU 应力模拟

CPU应力仿真通过并行工作进程执行密集的密码学操作，使可用CPU核心在指定时间内达到高CPU使用率。

工作原理

仿真生成了工作进程（使用 Python 的 multiprocessing）执行密集的SHA-256哈希计算，形成紧凑的循环。与主异步事件循环不同，这些工作进程可以充分利用多个 CPU 核而不阻碍应用程序的请求处理。

仪表盘控制

  • 持续时间： 压力测试需要多长时间（至少1秒）
  • 强度： 中等或高——控制并行工人数量
  • 启动/停止： 开始或取消模拟

你将观察到的内容

度规 意料之中 解释
CPU % 高（取决于强度） 消耗 CPU 周期的工人进程
记忆 略有增加 工作进程内存占用较小
延迟 可能会略有增加 请求处理的可用 CPU 减少

现实世界的 CPU 问题

生产 CPU 高通常由以下原因引起：

  • 低效算法（当O（n）可能时为O（n²）
  • 由于bug导致的无限循环
  • 过度正则表达式回溯
  • 大数据集下的未优化数据处理
  • CPU-bound 操作阻挡事件循环，而不是被卸载

诊断工具

  • Azure App Service → 诊断和解决使用→ CPU 问题
  • Application Insights 性能刀
  • py-spy 用于分析 Python 进程
  • top / htop 用于实时 CPU 监控

📊 内存压力仿真

内存压力模拟分配并保存大字节数组，以展示内存消耗模式和垃圾回收行为。

工作原理

大型 bytearray 对象被分配并填充随机数据，以防止内存优化。这些分配被保存在列表中，模拟内存泄漏等问题分配模式。多个分配是累计的，直到明确发布。

仪表盘控制

  • 尺寸（MB）： 每点击分配的内存量
  • 分配： 添加一个新的内存块（累积）
  • 发布： 释放所有分配的区块

你将观察到的内容

度规 意料之中 解释
内存（MB） 按分配规模增加 图表反映了工作集的增加情况
CPU 短暂的峰值 内存分配与数据填充
发行后 内存丢失 Python 垃圾回收器回收内存

Python 内存管理

Python 使用自动内存管理和垃圾回收。主要考虑因素：

  • 即使发布后，大分配也不能立即返回操作系统
  • Python 的内存分配器维护小对象的池
  • 参考循环需要循环垃圾回收器进行清理
  • gc.collect() 可以强制垃圾回收，但不保证内存会返回操作系统

现实世界的记忆问题

  • 无限制地积累数据的集合（例如缓存、日志）
  • 防止垃圾回收的循环引用
  • 承载大型对象的全局变量
  • 事件处理程序或回调以保持引用的存活
  • 大文件读取完全加载到内存中

诊断工具

  • Azure App Service → 记忆工作组刀片
  • tracemalloc 用于在 Python 中跟踪内存分配
  • memory_profiler 用于逐行内存分析
  • objgraph 用于可视化对象引用

🧵 异步阻塞（事件循环饥饿）

异步阻塞模拟展示了Python中危险的“sync-over-async”反模式，即在异步函数内进行同步阻塞调用，冻结整个事件循环。

工作原理

模拟调用 time.sleep() （阻塞操作）在异步上下文中，而不是使用 await asyncio.sleep().这阻止了 Python 的单线程事件循环，导致：

  1. 事件循环线程被阻塞
  2. 所有其他异步操作都会冻结（包括其他请求）
  3. 收到的请求排队等待事件循环
  4. 请求延迟会大幅增加

仪表盘控制

  • 延迟时间： 每个阻断操作持续的时间
  • 计数： 并发阻断操作数量可生成
  • 启动/停止： 开始或取消模拟
⏱️ 时长说明： Python 的 asyncio 默认运行在单线程上。即使是少量阻塞操作也可能造成显著影响——比多线程框架中的线程池枯竭更为严重。

同步过非同步反模式

这些模式会阻碍事件循环，应避免：

# ❌ 坏 - 阻塞事件循环进口时间 非同步 防御 handle_request（）： 时间.睡眠（5） # 阻挡整个事件循环！返回“完成” 非同步 防御 fetch_data（）： response = requests.get（URL） # BLOCKS - 请求是同步的！返回 response.json（）
# ✅ 好 - 完全同步import asyncio 导入 httpx 非同步 防御 handle_request（）： 等待asyncio.sleep（5） # 将控制权交还给事件循环返回“完成” 非同步 防御 fetch_data（）： 与HTTPX不同步。AsyncClient（） 作为客户端： response = wait， client.get（URL） # 非阻塞 HTTP返回 response.json（）

你将观察到的内容

度规 意料之中 解释
CPU 低 事件循环在等待，没有工作
记忆 普通 没有发生内存泄漏
待完成任务 可能会增加 等待事件循环的任务排队
延迟 🔴 秒数激增 等待事件循环的请求队列

为什么 CPU 低而延迟高

这就是事件循环阻塞的特征。 CPU 不起作用，因为事件循环被阻挡等待。新请求无法启动，因为单个事件循环已被占用。看起来应用处于空闲状态，但用户会遇到超时。

现实世界的原因

  • 在异步代码中使用同步库： requests.get() 代替 httpx 或 aiohttp
  • 呼唤 time.sleep() 代替 await asyncio.sleep()
  • 无同步文件I/O aiofiles
  • 无异步等效的同步数据库驱动程序
  • 内部阻挡的第三方库
  • CPU需要卸载到线程池的操作

如何修复

  • 用途 await 并且全线使用合适的异步库
  • 替换 requests 其中 httpx 或 aiohttp
  • 用途 asyncio.to_thread() 卸载阻断操作
  • 用途 aiofiles 用于异步文件操作
  • 使用异步数据库驱动程序（例如， asyncpg, aiomysql)

诊断工具

  • 所有端点的响应时间同时激增
  • Azure App Service → 诊断和解决问题
  • py-spy 查看事件循环线程的具体操作
  • 自定义异步事件环监控 loop.slow_callback_duration

🐌 慢速请求模拟器

慢速请求模拟器生成专门为画像仪训练和 Azure 诊断练习设计的长时间请求（每个约25秒）。

目的

与导致许多短块的异步阻塞模拟不同，这种方式会生成单个长请求，这些请求在分析器跟踪和监控仪表盘中清晰可见。延长的持续时间使得诊断工具中更容易捕捉这些症状。

仪表盘控制

  • 持续时间： 每个请求需要多长时间（5-60秒，默认25秒）
  • 间隔时间： 请求间隔时间
  • 最大请求： 总请求
  • 启动/停止： 开始或取消模拟

推荐设置

对于60秒的剖面仪追踪：

  • 持续时间： 25秒（允许在追踪窗口内捕获）
  • 中场休息： 10秒（多采样）
  • 最大请求： 6（不会让系统不堪重负）
⚠️ 排队时间说明： 如果事件循环被阻塞，你可能会在请求开始前看到额外的延迟。这是“队列时间”（等待事件循环）与“执行时间”（运行代码）。

配合 Azure 诊断使用

  1. 在Azure门户中启动CPU分析器追踪（60-120秒）
  2. 在仪表盘中点击🐌“开始慢速请求”
  3. 等待追踪完成
  4. 下载并分析——寻找长期运行的请求

参见 Azure 诊断指南 详细的剖面分析说明。

❌ 失败请求模拟

失败请求模拟产生 HTTP 个5xx错误，用于测试 Azure 诊断工具如 AppLens 和 Application Insights。

目的

该模拟生成 HTTP 500个内部服务器错误响应，具体表现为：

  • AppLens - Azure 门户 → 诊断和解决问题
  • Application Insights - 失效刀片
  • Azure 监视器 - 错误率警报

仪表盘控制

  • 错误计数： 需要生成的错误 HTTP 数为500（1-100）
  • 生成： 触发错误生成

例外类型

模拟会随机抛出各种例外类型：

例外 描述
ValueError提供的值无效
运行错误运行时错误发生
密钥错误词典中未找到密钥
索引错误指数超出范围
类型错误类型不匹配错误
属性错误未找到属性
零除错误除以零
连接错误连接中断

仪表盘事件日志

每个失败请求会在事件日志中显示：

  • 棕色 - 独特造型以提高可见度
  • ❌ 图标 - 请求失败指示器
  • 例外类型 - 被抛出的特定例外情况

参见 Azure 诊断指南 详细 AppLens 分析说明。

💥 撞车模拟

仪表盘包含碰撞模拟功能，用于测试 Azure 碰撞监控和容器重启行为。

🌐 语言选择（界面翻译）

仪表盘界面可以用以下支持的任何语言显示 Azure 认知服务翻译器.翻译在启动时由AI自动生成，并缓存以供后续请求使用。

⚠️ AI翻译通知： 翻译由 Azure 认知服务翻译器（机器翻译）生成，可能不完全准确。技术术语（例如， CPU、 WebSocket、 ThreadPool）在英语中被有意保留。

工作原理

  1. 设置 UI_LANGUAGE 环境变量 ISO 639-1 语言代码 （例如， es 西班牙语， fr 对于法语， ja 用于日语）
  2. 启动时，应用会检查该语言是否存在翻译过的本地文件
  3. 如果没有（或者英文源字符串发生了变化），它会调用 Azure Translator 生成一个
  4. 翻译后的文件被缓存——后续启动时使用缓存时，转换成本为零
  5. 仪表盘加载翻译后的字符串并应用到界面上

环境变量

变量名称 描述 默认
UI_LANGUAGE 仪表盘界面的 ISO 639-1 语言代码。设置为 en 英文版（无需翻译）。 en
TRANSLATOR_API_KEY Azure 认知服务翻译器订阅密钥。非英语语言必修。 （未设定）
TRANSLATOR_ENDPOINT 翻译器 API 端点URL。 https://api.cognitive.microsofttranslator.com
TRANSLATOR_REGION Azure 翻译资源的区域。 eastus
