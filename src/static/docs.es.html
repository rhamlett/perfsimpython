🎯 Simulador de Problemas de Rendimiento

Una Azure App Service educativa que Crea intencionadamente problemas de rendimiento para fines de aprendizaje y demostración.

Propósito

Esta aplicación está diseñada para ayudar a Azure App Service Ingenieros de Soporte y Asesores Técnicos:

📖
Aprende Cómo diagnosticar problemas comunes de rendimiento en Azure App Service
🔧
Práctica Uso de Azure herramientas de diagnóstico y monitorización
🎭
Demostrar Anti-patrones de rendimiento en un entorno controlado
👥
Tren Apoyar a los equipos en la identificación y resolución de problemas de rendimiento

⚠️ Advertencia: ¡Esta aplicación crea intencionadamente problemas de rendimiento!

  • 🔥 CPU estrés - Crea procesos de trabajo ejecutando operaciones intensivas para consumir CPU núcleos
  • 📊 Presión de memoria - Asigna y almacena bloques de memoria para aumentar el conjunto de trabajo
  • 🧵 Bloqueo de bucle de eventos - Utiliza sync-over-async anti-patrones para bloquear el bucle de eventos asíncronos de Python
  • 🐌 Solicitudes lentas - Genera solicitudes de larga duración para el análisis del perfilador
  • 💥 Caídas de aplicaciones - Provoca fallos mortales para pruebas Azure monitorización de accidentes
  • ❌ Solicitudes fallidas - Genera HTTP errores 5xx para probar AppLens y Application Insights

Solo despliega esta aplicación en entornos aislados y no de producción.

📊 Salpicadero

La aplicación incluye un panel de control en tiempo real en la URL raíz que muestra:

  • CPU Uso - Utilización actual del procesador
  • Memoria - Conjunto de trabajo (memoria física utilizada por el proceso)
  • Hilos activos - Recuento de hilos en el proceso
  • Tareas pendientes - Tareas de Asyncio en cola en el bucle de eventos
  • Latencia de petición - Tiempo de respuesta en tiempo real de la sonda (muestra el impacto del bloqueo del bucle de eventos)
  • Simulaciones activas - Actualmente ejecutando simulaciones de problemas

El panel utiliza WebSockets para actualizaciones en tiempo real e incluye un panel lateral con controles para activar cada tipo de simulación.

Indicadores métricos de color

Las fichas de métricas de CPU y Memoria utilizan codificación dinámica por colores para indicar los niveles de utilización de recursos:

Color Utilización Estado
Negro (por defecto) 0-60% Normal - los recursos están dentro del rango aceptable
Amarillo 60-80% Advertencia: uso elevado, niveles preocupantes
Rojo >80% Peligro: alto uso, posible agotamiento de recursos

IDs de registro de eventos y simulación

El Registro de Eventos en la parte inferior del panel registra toda la actividad de simulación con entradas codificadas por colores que coinciden con cada tipo de simulación. Los mensajes relacionados con una instancia específica de simulación se marcan con un subrayado punteado.

Visualización de IDs de simulación: Pasa el cursor sobre cualquier mensaje subrayado para revelar el ID completo de la simulación (GUID) en una descripción emergente. Este ID identifica de forma única cada instancia de simulación.

Uso de identificadores de simulación para la resolución de problemas:

  • El mismo ID de simulación se registra en el lado del servidor y aparece en Azure Application Insights y Log Analytics
  • Utiliza este ID para correlacionar eventos del panel con los registros del servidor al analizar problemas de rendimiento
  • Filtra Azure registros por ID de simulación para aislar la telemetría de una simulación específica
  • Véase el Azure Guía de diagnóstico para técnicas detalladas de correlación

⏱️ Monitor de latencia de solicitudes

El panel incluye un Monitor de Latencia de Solicitudes que demuestra cómo el bloqueo de bucles de eventos afecta al procesamiento real de peticiones. Los valores de latencia mostrados incluyen tanto el tiempo de cola como el tiempo de procesamiento.

Cómo funciona

  • Una tarea en segundo plano explora continuamente la /api/health/probe Punto final
  • La latencia se mide de extremo a extremo: solicitud enviada → respuesta recibida
  • Los resultados se transmiten vía WebSocket al panel de control en tiempo real

Lo que observarás

Estado Latencia Estado Explicación
Funcionamiento normal < 150ms 🟢 Bien Hilos de bucle de eventos disponibles
Bloqueo leve 150ms - 1s 🟡 Degradado Solicitudes en cola esperando el bucle de eventos
Bloqueo severo > 1s 🔴 Severo Retraso significativo en la cola
Tiempo muerto Años 30 🔴 Crítica Bucle de eventos completamente bloqueado

Por qué esto importa

Durante el bloqueo de bucles de eventos, las métricas de CPU y memoria suelen parecer normales, pero los usuarios experimentan una latencia severa. El monitor de latencia hace visible este problema invisible: puedes ver cómo los tiempos de respuesta aumentan de milisegundos a segundos al activar la simulación de bloqueo asincrónico.

🔥 CPU Simulación de tensiones

La simulación de CPU Stress genera un alto uso de CPU mediante procesos de trabajo paralelos que ejecutan operaciones criptográficas intensivas, saturando los núcleos de CPU disponibles durante un periodo determinado.

Cómo funciona

La simulación genera procesos de trabajo (usando Python multiprocessing) que ejecutan cálculos intensivos de hash SHA-256 en bucles cerrados. A diferencia del bucle principal de eventos asincónicos, estos procesos worker pueden utilizar completamente múltiples núcleos de CPU sin bloquear el manejo de peticiones por parte de la aplicación.

Controles del salpicadero

  • Duración: Cuánto tiempo realizar la prueba de esfuerzo (mínimo 1 segundo)
  • Intensidad: Moderado o Alto - controla el número de obreras paralelas
  • Inicio/Parada: Iniciar o cancelar la simulación

Lo que observarás

Métrica Esperado Explicación
CPU % Alta (depende de la intensidad) Procesos de trabajadores que consumen CPU ciclos
Memoria Ligero aumento Los procesos de trabajo tienen una huella de memoria pequeña
Latencia Puede aumentar ligeramente Menos CPU disponible para el procesamiento de solicitudes

Problemas CPU en el mundo real

La alta CPU en la producción suele estar causada por:

  • Algoritmos ineficientes (O(n²) cuando O(n) es posible)
  • Bucles infinitos debido a errores
  • Retroceso excesivo de expresión regular
  • Procesamiento de datos no optimizado con grandes conjuntos de datos
  • CPUoperaciones limitadas a - que bloquean el bucle de eventos en lugar de ser descargadas

Herramientas de diagnóstico

  • Azure App Service → Diagnosticar y Resolver Problemas → CPU Uso
  • Application Insights Hoja de rendimiento
  • py-spy para perfilar procesos en Python
  • top / htop para monitorización CPU en tiempo real

📊 Simulación de presión de memoria

La simulación de Presión de Memoria asigna y mantiene grandes matrices de bytes para demostrar patrones de consumo de memoria y comportamiento de recogida de basura.

Cómo funciona

Grande bytearray los objetos se asignan y rellenan con datos aleatorios para evitar la optimización de la memoria. Estas asignaciones se almacenan en una lista, simulando patrones problemáticos de asignación como fugas de memoria. Las asignaciones múltiples se acumulan hasta que se liberan explícitamente.

Controles del salpicadero

  • Tamaño (MB): Cantidad de memoria a asignar por clic
  • Asignar: Añade un nuevo bloque de memoria (acumulativo)
  • Estreno: Libera todos los bloques asignados

Lo que observarás

Métrica Esperado Explicación
Memoria (MB) Aumentos por tamaño de asignación Los gráficos reflejan el aumento del conjunto de trabajo
CPU Breve pico Asignación de memoria y relleno de datos
Tras el lanzamiento Caídas de memoria El recogedor de basura en Python recupera la memoria

Gestión de memoria en Python

Python utiliza gestión automática de memoria con recogida de basura. Consideraciones clave:

  • Las asignaciones grandes pueden no devolverse inmediatamente al sistema operativo ni siquiera después del lanzamiento
  • El asignador de memoria de Python mantiene pools para objetos pequeños
  • Los ciclos de referencia requieren que el recolector de basura cíclico limpie
  • gc.collect() puede forzar la recogida de basura pero no garantiza que la memoria se devuelva al sistema operativo

Problemas de memoria en el mundo real

  • Colecciones que acumulan datos sin límites (por ejemplo, cachés, registros)
  • Referencias circulares que impiden la recogida de basura
  • Variables globales que contienen objetos grandes
  • Gestionadores de eventos o callbacks manteniendo vivas las referencias
  • Las lecturas de archivos grandes cargadas completamente en memoria

Herramientas de diagnóstico

  • Azure App Service → hoja del conjunto de trabajo de memoria
  • tracemalloc para el seguimiento de asignaciones de memoria en Python
  • memory_profiler para análisis de memoria línea por línea
  • objgraph para visualizar referencias a objetos

🧵 Bloqueo asincrónico (Inanición de bucles de eventos)

La simulación de bloqueo asíncrono demuestra el peligroso anti-patrón "sync-over-async" en Python, donde se realizan llamadas de bloqueo síncronas dentro de funciones asíncronas, congelando todo el bucle de eventos.

Cómo funciona

Las llamadas de simulación time.sleep() (una operación de bloqueo) dentro de un contexto asíncrono en lugar de usar await asyncio.sleep(). Esto bloquea el bucle de eventos monohilo de Python, provocando:

  1. El hilo de bucle de eventos se bloquea
  2. TODAS las demás operaciones asíncronas se congelan (incluidas otras solicitudes)
  3. Las solicitudes entrantes se colocan en cola esperando el bucle de eventos
  4. La latencia de las peticiones aumenta drásticamente

Controles del salpicadero

  • Retraso (s): Cuánto dura cada operación de bloqueo
  • Conde: Número de operaciones de bloqueo simultáneas que aparecen
  • Inicio/Parada: Iniciar o cancelar la simulación
⏱️ Nota de duración: Por defecto, Python Asyncio funciona en un solo hilo. Incluso unas pocas operaciones de bloqueo pueden causar un impacto significativo — mucho más dramático que la falta de pool de hilos en frameworks multihilo.

El anti-patrón Sincronización sobre Asíncrona

Estos patrones bloquean el bucle de eventos y deben evitarse:

# ❌ MALO - Bloquea el bucle de eventosTiempo de importación Defensa asíncrona handle_request(): Tiempo.sueño(5) # ¡BLOQUEA todo el bucle del evento!volver "Hecho" Defensa asíncrona fetch_data(): respuesta = requests.get(url) # BLOQUES - ¡las peticiones son síncronas!volver response.json()
# ✅ BIEN - Correctamente asincrónicoimportar asincro Importar httpX Defensa asíncrona handle_request(): await asyncio.sleep(5) # Devuelve el control al bucle de eventosvolver "Hecho" Defensa asíncrona fetch_data(): ASINCRÓNICO con httpx. AsyncClient() como cliente: respuesta = esperar client.get(url) # No bloqueando HTTPvolver response.json()

Lo que observarás

Métrica Esperado Explicación
CPU BAJO El bucle de eventos está esperando, no funciona
Memoria Normal No se produce ninguna fuga de memoria
Tareas pendientes Puede aumentar Tareas en cola esperando el bucle de eventos
Latencia 🔴 De picos a segundos Solicitudes en cola esperando el bucle de eventos

Por qué CPU es baja pero la latencia alta

Esta es la firma del bloqueo de bucles de eventos. El CPU no funciona porque el bucle de eventos está bloqueado en espera. Las nuevas solicitudes no pueden iniciar porque el bucle de un solo evento está ocupado. Parece que la app está inactiva, pero los usuarios experimentan tiempos de espera.

Causas reales

  • Uso de bibliotecas síncronas en código asíncrono: requests.get() en lugar de httpx o aiohttp
  • Llamada time.sleep() en lugar de await asyncio.sleep()
  • E/S de archivos síncronas sin aiofiles
  • Controladores de bases de datos síncronas sin equivalentes asíncronos
  • Bibliotecas de terceros que bloquean internamente
  • CPUoperaciones intensivas que deberían descargarse a un pool de hilos

Cómo arreglar

  • Uso await con bibliotecas asincrónicas adecuadas a lo largo de todo
  • Reemplazar requests con httpx o aiohttp
  • Uso asyncio.to_thread() descargar operaciones de bloqueo
  • Uso aiofiles para operaciones de archivos asíncronas
  • Utiliza controladores de base de datos asincrónicos (por ejemplo, asyncpg, aiomysql)

Herramientas de diagnóstico

  • Los tiempos de respuesta aumentan para TODOS los puntos finales simultáneamente
  • Azure App Service → Diagnosticar y Resolver Problemas
  • py-spy para ver qué está haciendo el hilo del bucle de eventos
  • Monitorización personalizada de bucle de eventos asincónicos con loop.slow_callback_duration

🐌 Simulador de Peticiones Lentas

El Simulador de Peticiones Lentas genera peticiones de larga duración (~25 segundos cada una) diseñadas específicamente para la práctica de entrenamiento de perfiladores y Azure diagnóstico.

Propósito

A diferencia de la simulación de bloqueo asíncrono (que provoca muchos bloques cortos), esta crea solicitudes largas individuales que son claramente visibles en los trazos del perfilador y en los paneles de monitorización. La duración prolongada facilita capturarlos en herramientas de diagnóstico.

Controles del salpicadero

  • Duración(s): Cuánto tarda cada petición (5-60 segundos, por defecto 25)
  • Intervalo(s): Tiempo entre peticiones
  • Solicitudes máximas: Total de solicitudes para generar
  • Inicio/Parada: Iniciar o cancelar la simulación

Configuraciones recomendadas

Para un trazado de perfilador de 60 segundos:

  • Duración: 25 segundos (permite capturar dentro de la ventana de trazo)
  • Intervalo: 10 segundos (múltiples muestras)
  • Solicitudes máximas: 6 (no satura el sistema)
⚠️ Nota sobre el tiempo de espera: Si el bucle de eventos está bloqueado, puede que veas un retraso adicional antes de que comience la solicitud. Esto es "Tiempo de cola" (espera del bucle de eventos) frente a "Tiempo de ejecución" (ejecutar el código).

Uso con Azure Diagnóstico

  1. Inicia un trazado CPU Profiler (60-120 segundos) en Azure Portal
  2. Haz clic 🐌 en Iniciar solicitudes lentas en el panel de control
  3. Esperar a que el rastreo se complete
  4. Descarga y analiza - busca las solicitudes de larga duración

Véase el Azure Guía de diagnóstico Para instrucciones detalladas de análisis del perfilador.

❌ Simulación de solicitudes fallidas

La simulación de Solicitudes Fallidas genera HTTP errores 5xx para probar Azure herramientas de diagnóstico como AppLens y Application Insights.

Propósito

Esta simulación genera HTTP 500 respuestas de error interno del servidor que son visibles en:

  • AppLens - Azure Portal → Diagnosticar y resolver problemas
  • Application Insights - Hoja de fallos
  • Azure Monitor - Alertas de tasa de error

Controles del salpicadero

  • Recuento de errores: Número de HTTP 500 errores para generar (1-100)
  • Generar: Desencadena la generación de errores

Tipos de excepción

Registro de eventos del Panel

Cada solicitud fallida aparece en el Registro de Eventos con:

  • Color marrón - Estilo distintivo para la visibilidad
  • ❌ Icono - Indicador de solicitud fallida
  • Tipo de excepción - La excepción específica que se lanzó

💥 Simulación de accidentes

El panel incluye una función de simulación de fallos para probar Azure monitorización de fallos y el comportamiento de reinicio del contenedor.

⚠️ Advertencia: ¡Esto CANCELARÁ la solicitud!

Las simulaciones de accidentes terminan inmediatamente el proceso. Azure App Service reiniciará automáticamente la aplicación tras un fallo. Asegúrate de tener activado el control antes de provocar un cierre.

Tipos de accidentes disponibles

Tipo Descripción Caso de uso
exception Genera una excepción no gestionada que hace que el proceso se cierre Pruebas generales de choque (recomendable)
stackoverflow Recursión infinita que causa desbordamiento de pila Práctica de análisis de trazas de pila
oom Asigna memoria hasta que el proceso se bloquea Análisis de volcado de memoria
sigabrt Envía la señal SIGABRT para terminar el proceso Prueba de manejo de señales / Reinicio del Docker

Azure Configuración de Monitorización de Fallos

  1. En Azure Portal, ve a tu App Service
  2. Navega para diagnosticar y resolver problemas
  3. Busca "Application Crashes"
  4. Activa la monitorización de fallos si está disponible
  5. Provoca un bloqueo usando el panel de control
  6. Observa cómo el contenedor se reinicia y analiza los registros

⚙️ Configuración opcional

Puedes personalizar el comportamiento de la aplicación usando Azure App Service variables de entorno.

Tasa de Prueba de Salud

Controla con qué frecuencia el servidor envía sondas de salud para medir la latencia de las solicitudes. Todas las sondas se enrutan a través del frontend Azure para capturar latencias realistas de extremo a extremo.

Nombre de la variable Descripción Default
HEALTH_PROBE_RATE Intervalo de sonda en milisegundos. Mínimo 100ms. 200

Tiempo de espera en reposo

Cuando la aplicación está inactiva (sin conexiones al panel ni solicitudes de pruebas de carga), las sondas de salud se suspenden automáticamente para reducir el tráfico de red innecesario al frontend de Azurey a la telemetría Application Insights .

Nombre de la variable Descripción Default
IDLE_TIMEOUT_MINUTES Minutos de inactividad antes de suspender las sondas de salud. La actividad se reanuda automáticamente cuando se abre el panel de control o se recibe cualquier solicitud. 20

Pie de página personalizado

Establece un mensaje personalizado en el pie de página que aparezca en todas las páginas. El pie de página soporta HTML, lo que permite incluir enlaces.

Nombre de la variable Descripción
PAGE_FOOTER Contenido HTML para la segunda línea del pie de página. Si no está activado, solo se muestra la descripción de la app y la información de la build.

Valor de ejemplo:

Created by <a href="https://yoursite.com">Your Team</a> for training purposes

GitHub Enlace al Repositorio

Opcionalmente, muestra un enlace GitHub Repositorio en el menú de navegación de la barra lateral. El enlace está oculto por defecto. Cuando se proporcionan ambas variables de entorno, el enlace aparecerá en el menú y apuntará a https://github.com/{GITHUB_USER_NAME}/{GITHUB_REPO_NAME}.

Nombre de la variable Descripción
GITHUB_USER_NAME GitHub nombre de usuario o de la organización. Es necesario mostrar el enlace.
GITHUB_REPO_NAME GitHub nombre del repositorio. Es necesario mostrar el enlace.

Para configurarlos, navega hasta tu App Service en el Azure Portal, ve a Ajustes → variables de entorno, añade las variables, haz clic Solicita, entonces Confirmar.

🌐 Selección de idioma (Traducción de la interfaz)

La interfaz del panel de control puede mostrarse en cualquier idioma soportado por Azure Traductor de Servicios Cognitivos. Las traducciones se generan automáticamente al arrancar usando IA y se almacenan en caché para las solicitudes posteriores.

⚠️ Aviso de traducción de IA: Las traducciones son generadas por Azure Traductor de Servicios Cognitivos (traducción automática) y pueden no ser completamente precisas. Los términos técnicos (por ejemplo, CPU, WebSocket, ThreadPool) se conservan intencionadamente en inglés.

Cómo funciona

  1. Establece el UI_LANGUAGE variable de entorno a una Código de idioma ISO 639-1 (por ejemplo, es para español, fr para el francés, ja para japonés)
  2. Al iniciar, la app comprueba si existe un archivo de localización traducido para ese idioma
  3. Si no (o si las cadenas fuente en inglés han cambiado), llama a Azure traductor para generar una
  4. El archivo traducido se almacena en caché — los arranques posteriores utilizan la caché sin coste de traducción
  5. El panel carga las cadenas traducidas y las aplica a la interfaz
