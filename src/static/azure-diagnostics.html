☁️ Azure Diagnostics Guide

Diagnostic tools and techniques for identifying and resolving performance issues in Python applications

Quick Reference: Problem to Tool

Symptom Primary Tool Secondary Tools
High CPU usage App Service Diagnostics → CPU Analysis py-spy, cProfile
Memory growth Diagnose and Solve → Memory Analysis tracemalloc, memory_profiler
Slow responses Application Insights → Performance Request logs, dependency tracking
Application crashes Diagnose and Solve → Container Crash Application logs, stderr logs
HTTP 500 errors Application Insights → Failures Log Analytics, App Service logs

Azure Portal: Diagnose and Solve Problems

Accessing the Tool

  1. Open your App Service in Azure Portal
  2. Click "Diagnose and solve problems" in the left menu
  3. Select a detector category or use the search

Key Detectors for Performance

  • CPU Analysis - Identifies high CPU processes and patterns
  • Memory Analysis - Tracks memory usage and potential leaks
  • Container Crash - Investigates why containers are restarting
  • HTTP Server Errors - Analyzes 5xx error patterns
  • Web App Slow - Identifies latency causes

Application Insights

Setting Up Application Insights

Add the OpenCensus Azure Monitor exporter to your application:

pip install opencensus-ext-azure

Configure in your FastAPI application:

from opencensus.ext.azure.trace_exporter import AzureExporter
from opencensus.trace.samplers import AlwaysOnSampler

# Configure tracing
tracer = Tracer(
    exporter=AzureExporter(
        connection_string=os.getenv("APPLICATIONINSIGHTS_CONNECTION_STRING")
    ),
    sampler=AlwaysOnSampler()
)

Key Features

  • Performance - Request duration, dependency calls, response times
  • Failures - Exception tracking, failed requests, error rates
  • Live Metrics - Real-time performance monitoring
  • Application Map - Visual dependency graph
💡 Tip: Use the Transaction Search feature in Application Insights to trace specific requests end-to-end, including all dependency calls and their timing.

Kudu Console (Advanced Diagnostics)

Accessing Kudu

  1. Go to your App Service
  2. Click Advanced Tools → Go
  3. Or navigate to https://<app-name>.scm.azurewebsites.net

SSH Access

For Linux App Service, use SSH to access the container:

# From Kudu: Debug console → SSH
# Or use Azure CLI:
az webapp ssh --name <app-name> --resource-group <rg>

Useful SSH Commands

# View running processes
top -bn1

# Memory usage
free -m

# List Python processes
ps aux | grep python

# View application logs
tail -f /home/LogFiles/docker/*.log

Python Profiling Tools

py-spy (Sampling Profiler)

Best for CPU profiling in production without modifying code:

# Install in SSH session
pip install py-spy

# Profile running process
py-spy top --pid <python-pid>

# Record flame graph
py-spy record -o profile.svg --pid <python-pid>

cProfile (Built-in Profiler)

Add profiling to specific endpoints:

import cProfile
import pstats
import io

@app.get("/api/debug/profile")
async def profile_endpoint():
    pr = cProfile.Profile()
    pr.enable()
    
    # Your code here
    
    pr.disable()
    s = io.StringIO()
    pstats.Stats(pr, stream=s).sort_stats('cumulative')
    return {"profile": s.getvalue()}

tracemalloc (Memory Tracing)

Track memory allocations:

import tracemalloc

tracemalloc.start()

# Your code here

snapshot = tracemalloc.take_snapshot()
top_stats = snapshot.statistics('lineno')

for stat in top_stats[:10]:
    print(stat)

Log Analytics Queries (KQL)

Common Queries

Find slow requests:

requests
| where duration > 5000
| project timestamp, name, duration, resultCode
| order by duration desc

Error rate by endpoint:

requests
| where success == false
| summarize count() by name
| order by count_ desc

Container restarts:

ContainerAppSystemLogs_CL
| where Log_s contains "exited"
| project TimeGenerated, Log_s

Simulation-Specific Diagnostics

CPU Stress

When CPU stress is active, observe:

  • Metrics → CPU percentage spike
  • Diagnose → CPU Analysis shows worker processes
  • py-spy shows tight loops in calculation functions

Memory Pressure

When memory is allocated:

  • Metrics → Memory percentage increase
  • Diagnose → Memory Analysis shows process growth
  • tracemalloc shows large bytearray allocations

Blocking Operations

When blocking is active:

  • App Insights → Performance shows increased response times
  • Live Metrics shows requests queuing
  • Thread pool exhaustion visible in process stats

Application Crashes

After triggering a crash:

  • Container logs show exit code (137=OOM, 134=SIGABRT)
  • App Insights → Failures shows unhandled exceptions
  • Activity Log shows container restart events

Azure Load Testing

The Performance Problem Simulator includes a dedicated load testing endpoint designed for use with Azure Load Testing. This endpoint simulates realistic application behavior that degrades gracefully under load.

Load Test Endpoint

The /api/loadtest endpoint is designed to:

  • Perform sustained CPU work (interleaved SHA256 cycles at ~50% CPU per thread)
  • Hold memory buffers for entire request duration (creates visible memory pressure)
  • Degrade gracefully as concurrent requests increase (soft limit pattern)
  • Throw random exceptions after configurable threshold (default: 120 seconds at 20% probability)
  • Eventually trigger Azure's 230-second timeout under extreme load

Setting Up Azure Load Testing

  1. In the Azure Portal, create an Azure Load Testing resource
  2. Create a new test and configure the target URL
  3. Configure load pattern (ramp up, steady state, ramp down)
  4. Set up Azure Monitor integration to correlate metrics

GET with Query Parameters

Use the target URL directly — no JMeter script required:

# With defaults (tuned for Premium0V3)
https://your-app.azurewebsites.net/api/loadtest

# Custom parameters
https://your-app.azurewebsites.net/api/loadtest?workIterations=500&bufferSizeKb=10000

# Thread pool only (no CPU work)
https://your-app.azurewebsites.net/api/loadtest?workIterations=0&bufferSizeKb=100

Query Parameters Reference

ParameterDefaultDescription
workIterations200SHA256 iterations per CPU work cycle
bufferSizeKb20000Memory buffer held for request duration in KB
baselineDelayMs500Minimum request duration in ms
softLimit25Concurrent requests before degradation
degradationFactor500Delay ms per request over limit
errorAfter120Seconds before random errors may be thrown (0 disables)
errorPercent20Percentage chance (0-100) of random error after threshold

Understanding the Soft Limit

The soft limit creates a degradation curve where response times increase as concurrent requests exceed the threshold:

additionalDelay = max(0, concurrent - softLimit) × degradationFactor

Note: Actual response times will vary based on your Azure App Service tier, current load, and other factors. Use Azure Load Testing to establish baseline performance for your specific environment.

Diagnosing Load Test Results

1. Application Insights Integration

  • Go to Application Insights → Performance
  • Filter by operation name GET /api/loadtest
  • Observe response time percentiles (p50, p95, p99)
  • Check failure rates for the configurable random error threshold

2. Azure Monitor Metrics

  • Requests - Total request count and rate
  • Response Time - Average and percentile latencies
  • Http Server Errors - 5xx errors from random exceptions
  • CPU Percentage - Should increase with load

3. Load Testing Statistics

Query the stats endpoint during the test:

GET /api/loadtest/stats

{
  "currentConcurrentRequests": 127,
  "totalRequestsProcessed": 45230,
  "totalExceptionsThrown": 23,
  "averageResponseTimeMs": 847.5
}
