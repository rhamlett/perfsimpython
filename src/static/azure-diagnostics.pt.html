☁️ Azure Guia de Diagnóstico

Diagnosticar problemas de desempenho em Azure App Service usando ferramentas integradas e perfis Python

Referência rápida: Problema para Ferramenta

Sintoma Ferramenta Primária Ferramentas Secundárias
Alto uso CPU App Service Diagnóstico → CPU Análise py-spy, cProfile
Crescimento da memória Diagnosticar e Resolver → Análise de Memória tracemalloc, memory_profiler
Respostas lentas Application Insights → Desempenho Registros de solicitações, rastreamento de dependências
A aplicação trava Diagnosticar e Resolver → Falha do Container Logs de aplicação, logs stderr
HTTP 500 erros Application Insights → Fracassos Análise de Logs, App Service logs

Azure Portal: Diagnosticar e Resolver Problemas

Acessando a Ferramenta

  1. Abra sua App Service no Azure Portal
  2. Click "Diagnosticar e resolver problemas" No menu esquerdo
  3. Selecione uma categoria de detector ou use a busca

Detectores-chave para desempenho

  • CPU Análise- Identifica processos e padrões de alta CPU
  • Análise de Memória - Acompanha o uso de memória e possíveis vazamentos
  • Travamento do Container - Investiga por que os contêineres estão reiniciando
  • HTTP Erros de servidor - Analisa padrões de erro 5xx
  • Aplicativo Web Lento - Identifica causas de latência

Application Insights

Preparando Application Insights

  1. Crie o recurso Application Insights — No Portal Azure , procure por Application Insights, clique + Criar, escolha sua assinatura, grupo de recursos, região e um nome, então clique Revisar + criar.
  2. Pegue a corda de conexão — Uma vez que o recurso seja criado, abra-o e vá até o Visão geral página. Cópia do String de Conexão mostrado próximo ao topo da página.
  3. Adicione a variável ambiente ao seu App Service — No Portal Azure , navegue até sua App Service, vá para Configurações > variáveis de ambiente, e adicionar uma nova configuração de aplicativo com o nome APPLICATIONINSIGHTS_CONNECTION_STRING e colar a string de conexão como o valor. Click Candidate-se e confirmar o reinício.

Principais Recursos

  • Desempenho - Duração da solicitação, chamadas de dependência, tempos de resposta
  • Falhas - Rastreamento de exceções, requisições falhadas, taxas de erro
  • Métricas ao Vivo - Monitoramento de desempenho em tempo real
  • Mapa de Aplicação - Grafo de dependência visual

💡 Dica: Use o recurso de Busca de Transações em Application Insights para rastrear requisições específicas de ponta a ponta, incluindo todas as chamadas de dependência e seu timing.

🔗 Correlação do ID da Simulação

Cada instância de simulação recebe um único ID de simulação (GUID) que permite correlação de ponta a ponta entre a interface do painel e Azure diagnósticos.

Encontrando IDs de Simulação

No Painel: Passe o mouse sobre qualquer mensagem relacionada à simulação no Registro de Eventos (marcada com um sublinhado pontilhado) para ver o ID completo da Simulação em uma dica de ferramenta.

Em Azure: O mesmo ID de simulação é emitido nos logs do lado do servidor e pode ser encontrado em:

  • Application Insights - Rastreamentos de busca e eventos personalizados por ID de Simulação
  • Análise de Logs - Logs de consulta usando o ID como filtro
  • Troncos de Contêineres/App Service - Filtre stdout/stderr pelo GUID

Consultas de Correlação

Use estas consultas KQL no Log Analytics para correlacionar eventos do painel com a telemetria do servidor:

⚠️ Diferenças nos nomes das tabelas: Os espaços de trabalho do Log Analytics usam nomes de tabelas e colunas diferentes dos Application Insightsclássicos. Se você vir erros como "O nome 'traços' não se refere a nenhuma tabela conhecida", use os nomes do Log Analytics abaixo:

Clássico Application Insights Espaço de Trabalho de Análise de Logs
tracesAppTraces
customEventsAppEvents
requestsAppRequests
exceptionsAppExceptions
dependenciesAppDependencies
messageMessage
timestampTimeGenerated

// Find simulation start/end events by Simulation ID
AppEvents
| where Name in ("SimulationStarted", "SimulationEnded")
| where Properties["SimulationId"] == "YOUR-SIMULATION-ID-HERE"
| project TimeGenerated, Name, Properties
| order by TimeGenerated asc
// Find all requests during a simulation time window
let simStart = toscalar(
    AppEvents 
    | where Name == "SimulationStarted" and Properties["SimulationId"] == "YOUR-SIMULATION-ID-HERE"
    | project TimeGenerated);
let simEnd = toscalar(
    AppEvents 
    | where Name == "SimulationEnded" and Properties["SimulationId"] == "YOUR-SIMULATION-ID-HERE"
    | project TimeGenerated);
AppRequests
| where TimeGenerated between (simStart .. simEnd)
| order by TimeGenerated asc
// Find failed requests during a simulation
let simId = "YOUR-SIMULATION-ID-HERE";
let simEvents = AppEvents | where Properties["SimulationId"] == simId;
let simStart = toscalar(simEvents | where Name == "SimulationStarted" | project TimeGenerated);
let simEnd = toscalar(simEvents | where Name == "SimulationEnded" | project TimeGenerated);
AppRequests
| where TimeGenerated between (simStart .. simEnd)
| where Success == false
| project TimeGenerated, Name, ResultCode, DurationMs, Url
| order by TimeGenerated asc

Fluxo de Trabalho de Solução de Problemas

  1. Inicie uma simulação a partir do painel
  2. Passe o mouse sobre a mensagem de início no Log de Eventos para copiar o ID da Simulação
  3. Abrir Azure Portal → Application Insights → Logs (ou Análise de Logs)
  4. Consulte logs usando o ID de simulação para ver toda a atividade relacionada do lado do servidor
  5. Correlacione carimbos de tempo entre eventos do painel e métricas de servidor

💡 Dica: O ID de Simulação ajuda a isolar a telemetria ao executar múltiplas simulações simultâneas ou quando o painel é usado por múltiplos usuários.

Kudu Console (Diagnóstico Avançado)

Acessando Kudu

  1. Vá para sua App Service
  2. Click Ferramentas Avançadas → Vai
  3. Ou navegar para https://<app-name>.scm.azurewebsites.net

Acesso SSH

Para App Servicedo Linux, use SSH para acessar o container:

# From Kudu: Debug console → SSH
# Or use Azure CLI:
az webapp ssh --name <app-name> --resource-group <rg>

Comandos SSH úteis

# View running processes
top -bn1

# Memory usage
free -m

# List Python processes
ps aux | grep python

# View application logs
tail -f /home/LogFiles/docker/*.log

Ferramentas de Perfil em Python

py-spy (Perfilador de Amostragem)

Melhor para CPU perfilamento em produção sem modificar código:

# Install in SSH session
pip install py-spy

# Profile running process
py-spy top --pid <python-pid>

# Record flame graph
py-spy record -o profile.svg --pid <python-pid>

cProfile (Perfilador Embutido)

Adicione perfilamento a endpoints específicos:

import cProfile
import pstats
import io

@app.get("/api/debug/profile")
async def profile_endpoint():
    pr = cProfile.Profile()
    pr.enable()
    
    # Your code here
    
    pr.disable()
    s = io.StringIO()
    pstats.Stats(pr, stream=s).sort_stats('cumulative')
    return {"profile": s.getvalue()}

tracemalloc (Rastreamento de Memória)

Rastreie alocações de memória:

import tracemalloc

tracemalloc.start()

# Your code here

snapshot = tracemalloc.take_snapshot()
top_stats = snapshot.statistics('lineno')

for stat in top_stats[:10]:
    print(stat)

Consultas de Análise de Logs (KQL)

Consultas Comuns

Encontre pedidos lentos:

requests
| where duration > 5000
| project timestamp, name, duration, resultCode
| order by duration desc

Taxa de erro por endpoint:

requests
| where success == false
| summarize count() by name
| order by count_ desc

Reinício do contêiner:

ContainerAppSystemLogs_CL
| where Log_s contains "exited"
| project TimeGenerated, Log_s

Diagnósticos Específicos de Simulação

CPU Estresse

Quando CPU estresse estiver ativo, observe:

  • Métricas → CPU aumento percentual
  • Análise de → CPU de diagnóstico mostra processos de trabalhadores
  • O Py-Spy mostra laços apertados nas funções de cálculo

Pressão de Memória

Quando a memória é alocada:

  • Métricas → Aumento percentual de memória
  • Diagnóstico → Análise de Memória mostra crescimento do processo
  • Tracemalloc mostra grandes alocações de bytearis

Operações de Bloqueio

Quando o bloqueio está ativo:

  • App Insights → Performance mostra tempos de resposta aumentados
  • Métricas ao vivo mostra a fila de requisições
  • Exaustão do pool de threads visível nas estatísticas do processo

Falhas de Aplicação

Após desencadear um travamento:

  • Os logs dos contêineres mostram código de saída (137=OOM, 134=SIGABRT)
  • App Insights → Falhas mostra exceções não tratadas
  • O Registro de Atividades mostra eventos de reinício de contêineres
