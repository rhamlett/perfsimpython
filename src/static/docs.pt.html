🎯 Simulador de Problemas de Desempenho

Uma aplicação Azure App Service educacional que cria intencionalmente problemas de desempenho para fins de aprendizado e demonstração.

Propósito

Esta aplicação foi projetada para ajudar Azure App Service Engenheiros de Suporte e Consultores Técnicos:

📖
Aprenda Como diagnosticar problemas comuns de desempenho em Azure App Service
🔧
Prática Usando Azure ferramentas de diagnóstico e monitoramento
🎭
Demonstrar Anti-padrões de desempenho em um ambiente controlado
👥
Trem Apoiar as equipes na identificação e resolução de problemas de desempenho

⚠️ Aviso - Este aplicativo cria intencionalmente problemas de desempenho!

  • 🔥 CPU estresse - Cria processos de trabalho executando operações intensivas para consumir CPU núcleos
  • 📊 Pressão de memória - Aloca e mantém blocos de memória para aumentar o conjunto de trabalho
  • 🧵 Bloqueio de loop de eventos - Usa sync-over-async anti-padrões para bloquear o ciclo de eventos assíncro do Python
  • 🐌 Pedidos lentos - Gera solicitações de longa duração para análise de perfiladores
  • 💥 A aplicação trava - Desencadeia falhas fatais para testes Azure Monitoramento de Acidentes
  • ❌ Pedidos fracassados - Gera HTTP erros 5xx para testes de AppLens e Application Insights

Implante essa aplicação apenas em ambientes isolados e não produtivos.

📊 Painel

A aplicação inclui um painel em tempo real na URL raiz que mostra:

  • CPU uso - Utilização atual do processador
  • Memória - Conjunto de trabalho (memória física usada pelo processo)
  • Threads ativos - Contagem de threads no processo
  • Tarefas pendentes - Tarefas Asyncio enfileiradas no ciclo de eventos
  • Latência de solicitação - Tempo de resposta da sonda em tempo real (mostra o impacto do bloqueio de loop de eventos)
  • Simulações ativas - Atualmente executando simulações de problemas

O painel utiliza WebSockets para atualizações em tempo real e inclui um painel lateral com controles para acionar cada tipo de simulação.

Indicadores de Cor Métrica

Os blocos de métricas CPU e Memória usam codificação dinâmica de cores para indicar os níveis de utilização de recursos:

Cor Utilização Status
Preto (padrão) 0-60% Normal - os recursos estão dentro do alcance aceitável
Amarelo 60-80% Aviso - uso elevado, aproximando-se de níveis preocupantes
Vermelho >80% Perigo - alto uso, potencial esgotamento de recursos

IDs de Registro de Eventos e Simulação

O Registro de Eventos na parte inferior do painel registra toda a atividade da simulação com entradas codificadas por cores que correspondem a cada tipo de simulação. Mensagens relacionadas a uma instância específica de simulação são marcadas com um sublinhado pontilhado.

Visualizando IDs de Simulação: Passe o mouse sobre qualquer mensagem sublinhada para revelar o ID completo da Simulação (GUID) em uma dica de ferramenta. Esse ID identifica de forma única cada instância de simulação.

Uso de IDs de Simulação para Solução de Problemas:

  • O mesmo ID de simulação é registrado do lado do servidor e aparece no Azure Application Insights e no Log Analytics
  • Use esse ID para correlacionar eventos do painel com logs de servidores ao analisar problemas de desempenho
  • Filtre Azure logs pelo ID de Simulação para isolar a telemetria de uma execução de simulação específica
  • Veja o Azure Guia de Diagnóstico para técnicas detalhadas de correlação

⏱️ Monitor de Latência de Solicitação

O painel inclui um Monitor de Latência de Requisição que demonstra como o bloqueio de loop de eventos afeta o processamento de requisições no mundo real. Os valores de latência mostrados incluem tanto o tempo de fila quanto o tempo de processamento.

Como Funciona

  • Uma tarefa em segundo plano sonda continuamente o /api/health/probe Ponto final
  • A latência é medida de ponta a ponta: solicitação enviada → resposta recebida
  • Os resultados são transmitidos via WebSocket para o painel em tempo real

O que você vai observar

Condição Latência Status Explicação
Operação normal < 150ms 🟢 Bom Threads de loop de eventos disponíveis
Bloqueio leve 150ms - 1s 🟡 Degradado Requisições enfileiradas aguardando o ciclo de eventos
Bloqueio severo > 1s 🔴 Severo Atraso significativo na fila
Tempo Anos 30 🔴 Crítica Loop de eventos completamente bloqueado

Por que isso importa

Durante o bloqueio de loop de eventos, métricas de CPU e memória frequentemente parecem normais, mas os usuários experimentam latência severa. O monitor de latência torna esse problema invisível visível — você pode ver os tempos de resposta dispararem de milissegundos a segundos ao acionar a simulação de bloqueio assíncrono.

🔥 CPU Simulação de Estresse

A simulação CPU Stress cria alto uso de CPU por meio de processos paralelos de trabalho que executam operações criptográficas intensivas, saturando núcleos CPU disponíveis por um período especificado.

Como Funciona

A simulação gera processos worker (usando Python multiprocessing) que executam cálculos intensivos de hash SHA-256 em ciclos apertados. Diferentemente do principal ciclo de eventos assíncrono, esses processos worker podem utilizar totalmente múltiplos núcleos CPU sem bloquear o tratamento das requisições pela aplicação.

Controles do Painel

  • Duração: Quanto tempo fazer o teste de estresse (mínimo 1 segundo)
  • Intensidade: Moderado ou Alto - controla o número de trabalhadores paralelos
  • Início/Parada: Iniciar ou cancelar a simulação

O que você vai observar

Métrica Esperado Explicação
CPU % Alta (depende da intensidade) Processos de trabalhadores consumindo CPU ciclos
Memória Leve aumento Processos de trabalho têm pequena área de memória
Latência Pode aumentar um pouco Menos CPU disponível para processamento de solicitações

Questões CPU do Mundo Real

Alta CPU na produção é tipicamente causada por:

  • Algoritmos ineficientes (O(n²) quando O(n) é possível)
  • Loops infinitos devido a bugs
  • Retrocesso excessivo de expressões regulares
  • Processamento de dados não otimizado com grandes conjuntos de dados
  • CPUoperações limitadas bloqueando o ciclo de eventos em vez de serem descarregadas

Ferramentas de Diagnóstico

  • Azure App Service → Diagnosticar e Resolver Problemas → CPU Uso
  • Application Insights Lâmina de desempenho
  • py-spy para perfilar processos em Python
  • top / htop para monitoramento CPU em tempo real

📊 Simulação de Pressão de Memória

A simulação de Pressão de Memória aloca e mantém grandes arrays de bytes para demonstrar padrões de consumo de memória e comportamento de coleta de lixo.

Como Funciona

Grande bytearray Os objetos são alocados e preenchidos com dados aleatórios para evitar a otimização da memória. Essas alocações são mantidas em uma lista, simulando padrões problemáticos de alocação, como vazamentos de memória. Múltiplas alocações são cumulativas até serem explicitamente divulgadas.

Controles do Painel

  • Tamanho (MB): Quantidade de memória a ser alocada por clique
  • Alocar: Adiciona um novo bloco de memória (cumulativo)
  • Lançamento: Libera todos os blocos alocados

O que você vai observar

Métrica Esperado Explicação
Memória (MB) Aumentos pelo tamanho da alocação Os gráficos refletem o aumento do conjunto de trabalho
CPU Breve pico Alocação de memória e preenchimento de dados
Após o lançamento Quedas de memória Coletor de lixo em Python recupera memória

Gerenciamento de Memória em Python

Python utiliza gerenciamento automático de memória com coleta de lixo. Principais considerações:

  • Grandes alocações podem não ser retornadas imediatamente ao sistema operacional mesmo após o lançamento
  • O alocador de memória do Python mantém pools para objetos pequenos
  • Ciclos de referência exigem que o coletor de lixo cíclico limpe
  • gc.collect() pode forçar a coleta de lixo, mas não garante que a memória seja devolvida ao sistema operacional

Problemas de Memória no Mundo Real

  • Coleções que acumulam dados sem limites (por exemplo, caches, logs)
  • Referências circulares que impedem a coleta de lixo
  • Variáveis globais que contêm objetos grandes
  • Gerenciadores de eventos ou callbacks mantendo as referências vivas
  • Leituras de arquivos grandes carregadas inteiramente na memória

Ferramentas de Diagnóstico

  • Azure App Service → Lâmina do Conjunto de Trabalho de Memória
  • tracemalloc para acompanhamento de alocações de memória em Python
  • memory_profiler para análise de memória linha por linha
  • objgraph para visualizar referências a objetos

🧵 Bloqueio Assíncrono (Inanição de Loops de Eventos)

A simulação de Bloqueio Assíncrono demonstra o perigoso anti-padrão "sync-over-async" em Python, onde chamadas de bloqueio síncrono são feitas dentro de funções assíncronas, congelando todo o ciclo de eventos.

Como Funciona

As chamadas de simulação time.sleep() (uma operação de bloqueio) dentro de um contexto assíncrono em vez de usar await asyncio.sleep(). Isso bloqueia o ciclo de eventos single-threaded do Python, causando o seguinte:

  1. A thread do loop de eventos fica bloqueada
  2. TODAS as outras operações assíncronas travam (incluindo outros pedidos)
  3. Solicitações recebidas entram em fila aguardando o ciclo de eventos
  4. Latência de requisição dispara dramaticamente

Controles do Painel

  • Atraso(s): Quanto tempo dura cada operação de bloqueio
  • Conda: Número de operações de bloqueio simultâneas a serem criadas
  • Início/Parada: Iniciar ou cancelar a simulação
⏱️ Nota sobre a Duração: O assínpio do Python roda em uma única thread por padrão. Mesmo algumas operações de bloqueio podem causar impacto significativo — muito mais dramático do que a falta de pool de threads em frameworks multithreaded.

O Anti-Padrão Sincronizado sobre Assíncrono

Esses padrões bloqueiam o ciclo de eventos e devem ser evitados:

# ❌ RUIM - Bloqueia o ciclo de eventosTempo de importação Defesa assíncrona handle_request(): tempo.sono(5) # BLOQUEIA todo o loop do evento!retorno "Feito" Defesa assíncrona fetch_data(): resposta = requests.get(url) # BLOCOS - pedidos são síncronos!retorno response.json()
# ✅ BOM - Corretamente assíncronoimportar assínpio importação httpx Defesa assíncrona handle_request(): aguardar asyncio.sleep(5) # Retorna o controle ao ciclo de eventosretorno "Feito" Defesa assíncrona fetch_data(): ASSÍNCRONO com httpx. AsyncClient() como cliente: resposta = aguardar cliente.get(url) # Não bloqueando HTTPretorno response.json()

O que você vai observar

Métrica Esperado Explicação
CPU BAIXO O loop de eventos está esperando, não está funcionando
Memória Normal Nenhum vazamento de memória ocorrendo
Tarefas pendentes Pode aumentar Tarefas enfileiradas aguardando o ciclo de eventos
Latência 🔴 Picos para segundos Requisições enfileiradas aguardando o ciclo de eventos

Por que CPU é baixo, mas a latência é alta

Essa é a assinatura do bloqueio de loops de eventos. O CPU não está funcionando porque o loop de eventos está bloqueado na espera. Novas requisições não podem iniciar porque o ciclo de evento único está ocupado. Parece que o app está inativo, mas os usuários experimentam tempos de espera.

Causas do Mundo Real

  • Usando bibliotecas síncronas em código assíncrono: requests.get() em vez de httpx ou aiohttp
  • Chamados time.sleep() em vez de await asyncio.sleep()
  • E/S síncrono de arquivos sem aiofiles
  • Drivers de banco de dados síncronos sem equivalentes assíncronos
  • Bibliotecas de terceiros que bloqueiam internamente
  • CPUoperações - intensivas que devem ser descarregadas para um pool de threads

Como Consertar

  • Uso await com bibliotecas assíncronas adequadas ao longo de todo o jogo
  • Substituir requests com httpx ou aiohttp
  • Uso asyncio.to_thread() para descarregar operações de bloqueio
  • Uso aiofiles para operações de arquivos assíncronos
  • Use drivers de banco de dados assíncronos (por exemplo, asyncpg, aiomysql)

Ferramentas de Diagnóstico

  • Os tempos de resposta disparam para TODOS os endpoints simultaneamente
  • Azure App Service → Diagnosticar e Resolver Problemas
  • py-spy para ver o que o thread do loop de eventos está fazendo
  • Monitoramento personalizado de loop de eventos assíncronos com loop.slow_callback_duration

🐌 Simulador de Solicitação Lenta

O Slow Request Simulator gera requisições de longa duração (~25 segundos cada) especificamente projetadas para treinamento de perfiladores e prática de diagnósticos Azure .

Propósito

Diferente da simulação de Bloqueio Assíncrono (que causa muitos blocos curtos), isso cria requisições longas individuais que são claramente visíveis em rastreamentos de perfiladores e painéis de monitoramento. A duração estendida facilita capturá-los em ferramentas de diagnóstico.

Controles do Painel

  • Duração(s): Quanto tempo cada requisição leva (5-60 segundos, padrão 25)
  • Intervalo(s): Tempo entre os pedidos
  • Pedidos Máximos: Total de solicitações para gerar
  • Início/Parada: Iniciar ou cancelar a simulação

Configurações Recomendadas

Para um rastreamento de perfilador de 60 segundos:

  • Duração: 25 segundos (permite captura dentro da janela de rastreamento)
  • Intervalo: 10 segundos (múltiplas amostras)
  • Pedidos Máximos: 6 (não sobrecarrega o sistema)
⚠️ Nota sobre o tempo de fila: Se o loop de eventos estiver bloqueado, você pode ver atraso adicional antes do início da solicitação. Isso é "Tempo de Fila" (aguardando o ciclo de evento) versus "Tempo de Execução" (rodando o código).

Uso com Azure Diagnósticos

  1. Inicie um rastreamento CPU Profiler (60-120 segundos) no Azure Portal
  2. Clique 🐌 em Iniciar Solicitações Lentas no painel
  3. Espere o rastreamento ser concluído
  4. Baixe e analise - procure os pedidos de longa duração

Veja o Azure Guia de Diagnóstico Para instruções detalhadas de análise do perfilador.

💥 Simulação de Colisão

O painel inclui um recurso de Simulação de Falhas para testar Azure monitoramento de falhas e comportamento de reinicialização de contêineres.

⚠️ Aviso - Isso vai ENCERRAR a inscrição!

Simulações de colisão encerram imediatamente o processo. Azure App Service reinicia automaticamente o aplicativo após um travamento. Certifique-se de ter o monitoramento ativado antes de acionar um travamento.

Tipos de Colisão Disponíveis

Tipo Descrição Caso de Uso
exception Levanta uma exceção não tratada que trava o processo Testes gerais de colisão (recomendado)
stackoverflow Recursão infinita causando overflow de pilha Prática de análise de traços de pilha
oom Aloca memória até que o processo trave Análise de despejo de memória
sigabrt Envia sinal SIGABRT para encerrar o processo Testando o manuseio de sinais / Reinício do Docker

Azure Configuração de Monitoramento de Falhas

  1. No Azure Portal, vá até sua App Service
  2. Navegue para Diagnosticar e Resolver Problemas
  3. Procure por "Application Crashes"
  4. Ativer o monitoramento de falhas, se disponível
  5. Desencadeie um travamento usando o painel
  6. Observe o reinício do contêiner e analise os registros

Você pode personalizar o comportamento da aplicação usando Azure App Service variáveis de ambiente.

Taxa de Sondagem de Saúde

Controle com que frequência o servidor envia sondas de saúde para medir a latência das requisições. Todas as sondas são roteadas pelo frontend Azure para capturar latência realista de ponta a ponta.

Nome da variável Descrição Padrão
HEALTH_PROBE_RATE Intervalo de sonda em milissegundos. Mínimo 100ms. 200

Tempo de inatividade

Quando a aplicação está ociosa (sem conexões no painel ou requisições de teste de carga), as sondas de saúde são automaticamente suspensas para reduzir o tráfego desnecessário de rede para a interface e a telemetria Application Insights da Azure.

Nome da variável Descrição Padrão
IDLE_TIMEOUT_MINUTES Minutos de inatividade antes de suspender as sondas de saúde. A atividade é retomada automaticamente quando o painel é aberto ou qualquer solicitação é recebida. 20

Rodapé de página personalizado

Nome da variável Descrição

Exemplo de valor:

GitHub Link do Repositório

Opcionalmente, exiba um link GitHub Repositório no menu de navegação da barra lateral. O link está oculto por padrão. Quando ambas as variáveis de ambiente forem fornecidas, o link aparecerá no menu e apontará para https://github.com/{GITHUB_USER_NAME}/{GITHUB_REPO_NAME}.

Nome da variável Descrição
GITHUB_USER_NAME GitHub nome de usuário ou da organização. Obrigatório mostrar o link.

Para configurá-las, navegue até seu App Service no Azure Portal, vá em Configurações → variáveis de ambiente, adicione as variáveis, clique Candidate-se, então Confirme.

🌐 Seleção de Idioma (Tradução UI)

A interface do painel pode ser exibida em qualquer idioma suportado por Azure Tradutor de Serviços Cognitivos. As traduções são geradas automaticamente no início usando IA e armazenadas em cache para solicitações subsequentes.

⚠️ Aviso de Tradução por IA: As traduções são geradas por Azure Tradutor de Serviços Cognitivos (tradução automática) e podem não ser completamente precisas. Termos técnicos (por exemplo, CPU, WebSocket, ThreadPool) são intencionalmente preservados em inglês.

Como Funciona

  1. Defina o UI_LANGUAGE variável de ambiente para um Código da linguagem ISO 639-1 (por exemplo, es para espanhol, fr para o francês, ja para japonês)
  2. Ao iniciar, o app verifica se existe um arquivo de localização traduzido para aquele idioma
  3. Se não (ou se as strings de origem em inglês mudaram), ele chama Azure tradutor para gerar uma
  4. O arquivo traduzido é armazenado em cache — startups subsequentes usam o cache sem custo de tradução
  5. O painel carrega as strings traduzidas e as aplica à interface

Variáveis Ambientais

Nome da variável Descrição Padrão
UI_LANGUAGE Código de idioma ISO 639-1 para a interface do painel. Definir para en para o inglês (sem necessidade de tradução). en
TRANSLATOR_API_KEY Azure chave de assinatura do Tradutor de Serviços Cognitivos. Obrigatório para línguas que não são inglês. (não definido)
TRANSLATOR_ENDPOINT Tradutor API URL do endpoint. https://api.cognitive.microsofttranslator.com
TRANSLATOR_REGION Azure região do recurso Tradutor. eastus
